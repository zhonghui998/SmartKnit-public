# 系统架构说明

> 本文说明系统的分层设计与数据流，**不含**核心算法的实现细节。

## 1. 总体分层

```
前端定制器  →  业务层 API  →  ┬ 内容识别
                              ├ 生图服务
                              └ 针织化引擎
```

四层职责：

| 层 | 职责 | 不做什么 |
|---|---|---|
| 前端定制器 | 交互、预览、选区、换色操作 | 不做图像处理、不直连模型 |
| 业务层 API | 产品路由、规格解析、订单、生产交付 | 不写图像算法 |
| 生图服务 | 提示词构造、模型调用、失败兜底 | 不关心最终针数实现 |
| 针织化引擎 | 网格量化、区域渲染、产品合成 | 不关心图案从哪来 |

## 2. 核心设计：产品模板驱动

系统的可扩展性来自「**产品是数据，不是代码**」。

每个产品是一个 JSON 配置，声明：

- 成品尺寸、针织方法、目标针数
- 可用纱线色板
- 工艺极限：最多几色、最小可表达细节
- 图案在成品图上的位置与合成方式
- 商业信息：价格、成本、渠道商品映射

新增一个产品 = 加一个 JSON 文件，不改代码。

## 3. 核心设计：规格先行

这是系统最重要的一条原则：

> **先生成「这个产品能表达什么」的规格，再让 AI 按规格作画。**

规格包含五项：

| 项 | 来源 | 作用 |
|---|---|---|
| 目标针数 | 成品尺寸 × 针织密度 | 决定 AI 的构图尺度 |
| 色数上限 | min(画布容量, 工艺上限) | 决定色块数量 |
| 可用色板 | 照片主色吸附到实际纱线色 | 缩小 AI 的选色空间 |
| 最小色块 | 画布宽度 ÷ 20～40 | 低于此尺寸的细节必然消失 |
| 内容预算 | 由画布面积分档 | 小件禁场景、限主体数 |

同一份规格同时被三处消费：**生图阶段的提示词**、**换色面板的区域划分**、**生产输出的针数校验**。这样三处不会出现「面板上能改、织出来却没有」的错位。

## 4. 数据流：从照片到生产

```
① 上传照片
      │
② 内容识别 ── 文字/图标 ──→ 字体排版 ──┐
      │                                  │
      └── 图形/照片 ──→ AI 重绘 ────────┤
                                         │
③ 生成后归一：按画布比例处理 → 降到目标针数 → 简化到工艺可表达
                                         │
④ 针织化：量化到纱线色 → 网格化 → 输出针数级设计文件
                                         │
⑤ 合成预览：贴到真实产品图，联动袋身底色
                                         │
⑥ 客户微调：逐色换色 / 一键还原（像素级隔离）
                                         │
⑦ 下单 → 生产工单 → 工厂
```

## 5. 关键取舍

### 5.1 为什么 AI 之后还要「再处理一次」

模型不保证遵守输出尺寸（要求 82 针，实际给 1600×2848）。所以流程是：

1. 提示词里强制声明画布比例与最小色块
2. 生成后按画布比例归一，降到目标针数
3. 检测碎块密度，不达标就加大简化强度重算

**效果与模型的随机性解耦**，不再靠「碰运气」。

### 5.2 为什么换色要做像素级隔离

客户换了红色，如果整张图重绘，其他区域的颜色也会漂移（实测色差最高 42 级），客户会认为「你把我的图改了」。

所以换色只替换「与目标区域代表色相近」的格子，区域内暗部细节保留。

### 5.3 为什么大小产品用两套参数

| | 大件（≥2.5 万针） | 小件（<2.5 万针） |
|---|---|---|
| 简化强度 | 不做额外简化 | 自适应简化直到碎块归零 |
| 内容预算 | 允许场景、2 个主体 | 单主体、禁场景 |

原因：同样的碎块数量，在 270 针宽的画布上是 0.5% 的细节，在 162 针宽上就是 1% 的脏点——**感知阈值不同**。

## 6. 部署形态

- 单机可运行，无外部数据库依赖（配置与状态以文件组织）
- 生图服务与业务服务分离部署，便于单独扩容与替换模型
- 所有密钥通过环境变量注入，不落代码库
